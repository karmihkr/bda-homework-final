# Прогноз будущих WARN/ERROR по телеметрии

Исследовательский конвейер оценивает вероятность появления события уровня `WARN` или `ERROR` на сетевом узле в следующие 7 суток. Цель — прокси-разметка из логов, а не подтверждённая авария. Результаты сами по себе не доказывают эксплуатационную пользу: в предыдущем исследовании ROC-AUC около 0,5 не давал оснований для внедрения.

## Что есть в репозитории

- `telemetry_hw.py` — проверка, нормализация и аудит источников телеметрии.
- `telemetry_failure_modeling.py` — формирование временных срезов, обучение LR/XGBoost, выбор порога, test-оценка и SHAP.
- `config.json` — параметры окна, временных срезов, моделей, поиска и политики тревог.
- `architecture.md` — компоненты, потоки данных и хранение артефактов.
- `refactoring_report.md` — описание рефакторинга, идемпотентности и ограничений.
- `Dockerfile` — контейнер для воспроизводимого запуска.

## Данные

Входные данные не хранятся в GitHub. Конвейер ищет JSONL в `dataset/raw/telemetry/dt=*/` и `dataset/late_delivery/telemetry/dt=*/`. У каждого события нужны поля `node_id`, уровень `level`, время (`ts`, `timestamp`, `event_ts`, `datetime`, `time` или `event_time`) и показатели `load_pct`, `latency_ms`, `error_rate`.

Если преподаватель выдал учебный генератор, небольшой рабочий комплект можно подготовить так:

```bash
python -m generator.tdg --level S --out ./dataset --seed 20260827 --clean
```

Этот набор синтетический, не содержит реальных измерений и нужен только для воспроизводимости учебного задания. Генерация уровня S создаёт большой комплект; перед запуском проверьте свободное место. Если у вас есть выданный набор, используйте его и не публикуйте приватные данные.

## Установка

Требуются Python 3.12+ и зависимости из `requirements.txt`.

```bash
python -m venv .venv
source .venv/bin/activate       # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
```

## Запуск

Из корня репозитория:

```bash
python telemetry_failure_modeling.py
```

Входной каталог и папку результатов можно переопределить. Для быстрого технического прогона сократите число кандидатов поиска; это ускоряет запуск, но может изменить выбранные гиперпараметры и метрики, поэтому такой результат нельзя напрямую сравнивать с полным поиском.

```bash
python telemetry_failure_modeling.py \
  --dataset ./dataset \
  --output ./processed/telemetry_failure \
  --search-count 2
```

По умолчанию параметры читаются из `config.json`. `--config /path/to/config.json` задаёт другой конфиг; параметры CLI `--dataset`, `--output`, `--search-count` имеют приоритет. Если данные, конфигурация и код совпадают с последним успешным запуском, конвейер повторно использует артефакты. Укажите `--force`, чтобы переобучить модели.

## Docker

Сначала подготовьте каталог `dataset/` на компьютере. Затем соберите и запустите контейнер из корня проекта:

```bash
docker build -t bda-telemetry-risk .
mkdir -p processed/telemetry_failure
docker run --rm \
  -v "$PWD/dataset:/app/dataset:ro" \
  -v "$PWD/processed/telemetry_failure:/app/processed/telemetry_failure" \
  bda-telemetry-risk
```

Данные исключены из образа и Git. Выходной каталог примонтирован с хоста. Для принудительного пересчёта:

```bash
docker run --rm \
  -v "$PWD/dataset:/app/dataset:ro" \
  -v "$PWD/processed/telemetry_failure:/app/processed/telemetry_failure" \
  bda-telemetry-risk --force
```

## Этапы и выбор модели

1. `load_data` загружает и нормализует JSONL через существующий загрузчик, записывает аудит входных файлов.
2. `preprocess` создаёт признаки по истории строго до cutoff и временные train/validation/test срезы без перемешивания.
3. `train_model` сравнивает логистическую регрессию и базовый XGBoost, выбирает гиперпараметры XGBoost по AP на validation, затем замораживает порог тревоги по validation.
4. `evaluate` считает метрики на независимом test и создаёт диагностику, прогнозы и SHAP. Test не участвует в выборе модели, гиперпараметров или порога.
5. Артефакты записываются в каталог `--output`; журнал запуска — `pipeline.log`.

## Артефакты

Ключевые файлы в `processed/telemetry_failure/`:

| Файл | Содержание |
|---|---|
| `evaluation.json` | Метрики, описание данных/срезов, версии пакетов и проверки на утечку |
| `run_manifest.json` | SHA-256 входов, эффективной конфигурации и исходного кода для кэширования |
| `node_time_dataset.parquet` | Таблица узел × cutoff с признаками и будущей меткой |
| `selection_frozen.json` | Параметры поиска и validation-порог до открытия test |
| `validation_metrics`, `test_metrics` в `evaluation.json` | AP и ROC-AUC обеих базовых моделей и настроенной XGBoost на validation/test |
| `test_predictions.parquet`, `validation_predictions.parquet` | Оценки моделей на двух временных срезах |
| `logistic.joblib`, `xgb_baseline.joblib`, `xgb_tuned.joblib`, `xgb_tuned.ubj` | Сохранённые модели |
| `shap_summary.json`, `shap_importance.csv`, `shap_values.npz` | Глобальная и локальная SHAP-интерпретация |
| `error_groups.csv`, `error_slices.csv`, `false_positive_examples.csv` | Диагностика результатов и ложных тревог |
| `validation_suppression.json`, `alert_load.json` | Сценарии cooldown и расчёт предполагаемой нагрузки |
| `pipeline.log` | Журнал ключевых этапов и повторного использования результатов |

## Ограничения

- Цель — будущие сообщения `WARN/ERROR`, не подтверждённые инциденты.
- В исходной схеме нет `ingest_ts`; невозможно установить, была ли поздняя доставка доступна к cutoff.
- `ERROR` могут концентрироваться в одном дне, из-за чего оценка чувствительна к временному окну.
- Бюджет 20 тревог на 1000 прогнозов и cooldown 14 дней — учебные сценарии. При 45 000 узлов и недельном горизонте 20/1000 соответствуют примерно 129 тревогам в сутки до дедупликации; это не фактическая нагрузка смены.
- Синтетический комплект нельзя выдавать за данные сети оператора. Низкий ROC-AUC/AP не следует скрывать подбором порога.

## Что сделать перед сдачей

1. Убедиться, что `dataset/` доступен локально, но не попал в Git.
2. Выполнить команды проверки из `refactoring_report.md`.
3. Скопировать из `docker build` и `docker run` реальные результаты в отчёт; если Docker недоступен, указать это преподавателю, не заявлять о проверке контейнера.
4. Отправить коммиты в GitHub и сдать ссылку на репозиторий.
